Update — fixed: rebuilding used to silently wipe no-gps-location-resolver results
------------------------------------------------------------------------------------
Your query (verbatim)
"update travel-journal-2026-01-14/data/multimedia/multimedia-data.json"

Claude's resolved query
Ran this script with no arguments (a full rebuild) to fulfil that request.
It overwrote every record's resolved_location that had source
"subject_inferred" — the field scripts/python/no-gps-location-resolver/
writes by matching landmark names in caption text for files with no GPS —
back to "no_gps", discarding 695 records' worth of location work (486
from earlier sessions, 209 from the Stockholm gazetteer extension earlier
this session) in one run. This was a genuine bug in build(), not intended
behavior: load_existing_datafile()'s merge logic only ever special-cased
`prior resolved_location.source == "internet_geocode"` when deciding
whether to keep a prior run's resolved_location over a fresh
recomputation. A "subject_inferred" record has no GPS at all -- that's
the entire reason the resolver had to infer it from text in the first
place -- so a fresh run of THIS script can only ever recompute "no_gps"
for it, never anything better. Nothing in the merge logic accounted for
that, so every plain rerun silently regressed every resolver-inferred
location.

Fixed in build(): prior_source == "subject_inferred" is now always kept,
unconditionally (unlike the internet_geocode case, there's no scenario
where the fresh recomputation is preferable). See the shared
Instructions.txt's "Fixed: rebuilding used to silently wipe
no-gps-location-resolver results" section, and the inline comment at that
check in the script itself, for the full reasoning. This fix now applies
to every trip, not just this one.

Recovery this session: restored data/multimedia/multimedia-data.json from

Stockholm gazetteer extension's --in-place run), then reran
