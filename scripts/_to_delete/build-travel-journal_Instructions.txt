Your message left the actual range as the literal placeholder

Built scripts/javascript/build-travel-journal.js, a plain Node script (no
npm dependencies, but shells out to poppler's `pdftoppm`; not a two-step,
Claude-mediated script — see "PYTHON, NOT... / PLAIN NODE, NOT
CLAUDE-MEDIATED" reasoning below) that:

  1. Takes an inclusive start/end date range as two required command-line
     arguments (YYYY-MM-DD each) instead of a hardcoded range.
  2. Scans the photos/ folder for dated subfolders (YYYY-MM-DD) of
     multimedia files — photos AND videos, see "MANIFEST.JS NOW INCLUDES
     VIDEOS" below — and rewrites manifest.js (window.PHOTO_MANIFEST) from
     that scan.
  3. Scans the rideWithGPS/ folder for route-report PDFs named with a
     leading YYYY-MM-DD, rasterizing each to a PNG via `pdftoppm` (only
     when missing or stale) for embedding.
  4. Reads data/travel-details/travel-details.json and derives the
     multi-day "where you are" location bands (the "All Day" list items at
     the top of each day's Events list) automatically from its "locale"
     column, instead of a hand-transcribed LOCATION_BANDS constant — see
     "LOCATION BANDS: NOW DERIVED, NOT TRANSCRIBED" below.
  5. Writes index.html: one `<section class="day">` per calendar day in
     the given range (even days with nothing scheduled), each containing,
     in order: Events (build-time location-band items + client-side
     calendar events), Travel Details, Notes, a photo-gallery link with a
     live mini-map (if that date has a photo folder), and a Cycle Routes
     block (if that date has ride report PDFs).

This is a NEW script, not an edit of the old
scripts/_to_delete/build-journal.js. That file already lived in
_to_delete/ (marked for removal) before this task, so it was left alone;
build-travel-journal.js is written to fully replace it going forward.

PLAIN NODE, NOT CLAUDE-MEDIATED
-----------------------------------
Like its predecessor, this script needs no research or synthesis only
Claude can supply. Events, Notes, and Travel Details are NOT baked into
index.html at build time at all — they're populated entirely CLIENT-SIDE,
at page-load time, from data/events/events-data.js,
data/daily-notes/daily-notes-data.js, and
data/travel-details/travel-details-data.js respectively (the runtime
mirrors refresh-events.js, refresh-notes.js, and refresh-travel-details.py
each write alongside their own .json file). Re-running just one of those
three refresh scripts is enough for index.html to pick up new
events/notes/travel-details on next page load — you don't need to re-run
this script for that. Re-run THIS script only when: the date range itself
changes, photo folders or rideWithGPS PDFs are added/removed, or the
travel-details.json "locale" column changes in a way that should move a
location-band boundary.

LOCATION BANDS: NOW DERIVED, NOT TRANSCRIBED
-------------------------------------------------
The old build-journal.js required a manual step (see
scripts/_to_delete/TravelJournal_Instructions.txt, step 2.c) where Claude
hand-transcribed each multi-day "where you are" span into a LOCATION_BANDS
constant at the top of the script, reading them off a separate calendar
export. That's gone. This script instead groups calendar-CONSECUTIVE rows
in data/travel-details/travel-details.json that share the same trimmed,
non-empty "locale" string into one band automatically (computeLocationBands()
in the script). A gap in the data (a date with no row, or a row with a
blank locale) breaks the run, same as a locale value actually changing
does — it does not silently bridge across missing days.

Practical effect: band labels are now exactly whatever text is in
TravelDetails.ods's Locale column for that day (e.g. "Harlem NL", "Bike
and Barge", "Drive to Sweden") rather than hand-composed labels like
"Netherlands – Haarlem". Keep the Locale column worded the way you want it
to read on the journal page — this script no longer rewords it. A day
outside every band (no row, or a blank locale) simply gets no "All Day"
item, exactly like a day outside every old LOCATION_BANDS range used to.

Also new: a "Travel Details" block per day
-----------------------------------------------
index.html's day template now includes a "Travel Details" section (Trip,
Locale, Lodging, Transportation, Meals, Activities, Trip Notes — "Trip
Notes" rather than "Notes" so it isn't confused with the journal's own
Notes section right below it), populated client-side the same way Events
and Notes already are. This was added to index.html directly in prior
work in this project; build-travel-journal.js now generates it as a
built-in part of every rebuild, so a full regenerate no longer loses it.

MANIFEST.JS NOW INCLUDES VIDEOS (added 2026-08-25)
-------------------------------------------------------
Your query: "update manifest.js based on multimedia files in the photos
subfolder."

Claude's resolved query: scanPhotoFolders()'s file filter was IMAGE_RE
only (jpe?g|png|gif|webp|bmp|heic|heif|avif|svg) — a video sitting in a
photos/YYYY-MM-DD folder (e.g. a phone's .mp4 clip) was silently invisible
to manifest.js and didn't count toward that day's "N photos" link, even
though daily-location-gallery.html already fully supports embedding
videos (its own isVideo()/VIDEO_EXT_RE, a <video> tag with a "VIDEO"
badge, and mixed "N photos, M videos" count labels — it just doesn't read
manifest.js at all, so it was unaffected by this gap). I added VIDEO_RE
(mp4|mov|m4v|avi|webm|mkv — the same extension list, so a file
manifest.js now includes is exactly one gallery already knows how to
embed as a video) and now scan with MEDIA_RE = IMAGE_RE | VIDEO_RE.

Two other things changed alongside this, both downstream of the same
scan and left inconsistent otherwise:
  - Each day's photo-link label now splits into "N photos, M videos"
    (only the parts that are nonzero) instead of always saying "N
    photos" — matching daily-location-gallery.html's own label style. A
    day whose folder is all video no longer misreports "0 photos".
  - The header sub-line ("N days with photos · M photos total") splits
    the same way ("M photos, K videos total").

Ran on the real project: 5 videos turned up across photos/2026-07-05,
photos/2026-07-09 (x2), and photos/2026-07-10 (x2) — all previously
absent from manifest.js. See the "Second run" example below.

Known gap this does NOT fix: gallery.html (the standalone ?folder=<name>
viewer, not daily-location-gallery.html) reads manifest.js directly and
renders every entry with a plain `<img>` tag — it has no video handling,
so a video filename now in manifest.js will show as a broken image icon
there. It's a secondary/legacy tool (index.html's own day photo-links all
point to daily-location-gallery.html, which already handles video
correctly and doesn't use manifest.js at all), so this was left as-is
rather than expanding scope — flag it if you want gallery.html taught to
embed video too.

HOW TO RUN IT (current, as of the August 2026 shared-script move)
------------------------------------------------------------------------
    node scripts/javascript/build-travel-journal.js <journal-folder> <start> <end> [--title "Custom Title"]

  <journal-folder>  Which trip to build. Either a path (relative to the
                    current directory, or absolute) to a
                    travel-journal-YYYY-MM-DD/ folder, or just that
                    folder's name if it lives directly under the
                    travel-journals collection root (e.g.
                    "travel-journal-2026-07-01"). Required.
  <start>/<end>     Inclusive date range, YYYY-MM-DD. Both required.
  --title "text"    Optional. Sets this trip's <title>/<h1> text (the 🧳
                    emoji is always prefixed onto <h1> separately, so
                    don't include it here). If omitted, a trip that
                    already has an index.html keeps its current title
                    as-is -- a plain rebuild never clobbers a name
                    customized earlier (e.g. "Travel Journal 2026
                    Summer", travel-journal-2026-07-01's own title). A
                    trip with no index.html yet defaults to plain
                    "Travel Journal". See the update section at the end
                    of this file for the full reasoning.

Example (the July trip, matching its existing title):
    node scripts/javascript/build-travel-journal.js travel-journal-2026-07-01 2026-07-01 2026-08-18

Example (the January trip):
    node scripts/javascript/build-travel-journal.js travel-journal-2026-01-14 2026-01-14 2026-01-31

Example (setting/changing a trip's title explicitly):
    node scripts/javascript/build-travel-journal.js travel-journal-2026-07-01 2026-07-01 2026-08-18 --title "Travel Journal 2026 Summer"

Notes and safety
-------------------
- Read-only with respect to data/events/, data/daily-notes/, and
  data/travel-details/ — this script only READS travel-details.json (to
  derive location bands); it never writes to any of the three data
  sources or their refresh scripts. Run the relevant refresh-*.py/.js
  script first if you want this rebuild to reflect newer source data.
- Requires data/travel-details/travel-details.json to already cover (or
  at least overlap) the range you're rebuilding, if you want location
  bands — run refresh-travel-details.py first for a new/wider range. A
  missing or non-overlapping travel-details.json just means zero bands
  get derived, not an error.
- photos/ and rideWithGPS/ are scanned in full every run (not filtered to
  the given range up front) — a folder or PDF dated outside the requested
  range is simply never referenced by any day section, since only days
  inside [start, end] get rendered at all.

Update — retired: replaced by the former index-dynamic.html (August 2026)
------------------------------------------------------------------------------
Each trip had grown a second, client-side-rendered index-dynamic.html
alongside this script's build-time index.html (see that trip's own
index-dynamic.html top-of-script comment, at the time) -- a full twin
that computed its whole day-by-day skeleton, date range, and photo/video
counts live from the data/ folder on every page load, needing no rebuild
step at all after adding photos, events, notes, ride reports, or travel
details. Once that twin existed and worked, this script's own
build-time index.html was pure redundancy: two files to keep in sync,
one of which (this one) needed a rebuild after nearly every kind of data
change, the other needing none.

Per your request, each trip's old index.html was deleted and its
index-dynamic.html renamed to index.html in its place -- there is now
only one index.html per trip, and it's the client-side-rendered kind.
This script (build-travel-journal.js) is retired accordingly: moved to
scripts/_to_delete/, and nothing in the project calls it anymore.
refresh-notes.js used to run it automatically after merging notes (see
refresh-notes_Instructions.txt); that step was removed since it's no
longer needed -- notes-data.js is read live, the same as every other
data mirror this script used to require a rebuild to pick up.

Two things this script used to be the only source of, now handled
elsewhere:
  - Per-trip custom <title>/<h1> text (e.g. this trip's "Travel Journal
    2026 Summer") -- this script resolved it from --title, or the
    existing index.html's own title, or a plain default (see "Update —
    moved to scripts/javascript/..." above). The renamed index.html files
    already carry the right static <h1>/<title> text baked in from
    before the rename, so nothing needed to change there.
  - manifest.js (window.PHOTO_MANIFEST) -- this script's own scan of
    photos/ for gallery.html's ?folder= viewer. Nothing currently
    regenerates manifest.js going forward; it's frozen at whatever this
    script last wrote. gallery.html is a secondary/legacy tool (index.html's
    own photo-links all point at common/daily-location-gallery.html,
    which reads data/multimedia/multimedia-data.js directly, not
    manifest.js) -- if gallery.html's ?folder= listing needs to reflect
    photos added after this retirement, something will need to either
    regenerate manifest.js some other way or be pointed at
    multimedia-data.js instead.

If a future trip is ever built the old way (no index-dynamic.html-style
page written for it), this script would need un-retiring rather than
copied fresh -- it still works exactly as documented above, it's just
unused today.
