What the script does (current behavior)
-------------------------------------------
build-daily-location-gallery-for-range.js generates a date-range-scoped
VIEW of daily-location-gallery.html: the exact same page (same styling,
same behavior, same in-page ?date= day picker), restricted up front to
only the days whose date falls within [start, end] (inclusive, both
YYYY-MM-DD) — computed by filtering on the basename of each cluster's
"folder" field (e.g. "photos/2026-07-12" -> "2026-07-12"), plain string
comparison (YYYY-MM-DD sorts lexicographically = chronologically, so no
timezone-sensitive date parsing is needed).

IMPORTANT — this version's data is LIVE, not baked in:

  - The generated page still loads
    data/multimedia-location/multimedia-location-data.js at runtime —
    the exact same live runtime mirror daily-location-gallery.html
    itself loads. Immediately after that script tag, this script
    inserts one small extra <script> block that filters
    window.MULTIMEDIA_LOCATION_DATA down to just the clusters in
    [start, end], before any other page script reads it.

  - Because of that, if data/multimedia-location/multimedia-location-
    data.js is later regenerated (new days added, corrected overview-
    descriptions, re-clustered, etc., via
    scripts/javascript/build-multimedia-location-clusters-data.js),
    every range page generated by this script automatically reflects
    the update the next time it's opened in a browser — you do NOT need
    to rerun this script just because the underlying data changed.

  - The RANGE itself is still fixed at generation time. Rerun this
    script with different <start>/<end> arguments (or a different
    [output-path]) to get a page scoped to a different range.

  - Trade-off: because the page depends on the live
    data/multimedia-location/multimedia-location-data.js file (and on
    relative photo/video paths under photos/), the output is NOT a
    portable single-file artifact the way a fully self-contained
    snapshot would be. It must stay in the project root, next to data/
    and photos/, to work — you can't just hand someone this one HTML
    file on its own.

  - The script still prints a PREVIEW count (how many clusters/days
    currently fall in the range, read from
    data/multimedia-location/multimedia-location-data.json purely for
    that console message) so you have an idea of what the page will
    show right now — but that preview is not written into the output
    file, and the page's actual displayed data always reflects whatever
    the .js mirror says at the moment someone opens it, not what it said
    when this script ran.

Why it reads the live daily-location-gallery.html as its template,
instead of embedding its own copy of the markup/CSS/JS
------------------------------------------------------------------------
build-daily-multimedia-gallery.js (the sibling script for
daily-gallery.html) embeds its whole HTML/CSS/JS as one large string
constant inside the .js file itself. This script deliberately does NOT
copy that pattern, because daily-location-gallery.html is a large,
still-evolving page, and a second independent copy of its markup
embedded in this script would inevitably drift out of sync with the
real page over time (a future styling or behavior fix to
daily-location-gallery.html would silently NOT apply to range pages
unless someone remembered to update this script too).

Instead, this script reads the project root's own
daily-location-gallery.html at run time and does exactly one targeted
insertion: right after the

    <script src="./data/multimedia-location/multimedia-location-data.js" ...></script>

line (which loads ALL days from the runtime mirror), it inserts

    <script>
      (function () {
        var RANGE_START = "<start>", RANGE_END = "<end>";
        ...filters window.MULTIMEDIA_LOCATION_DATA down to that range...
      })();
    </script>

Every other byte of the page — CSS, map/gallery/lightbox/Read Aloud JS,
the day-picker/empty-state/entry-numbering logic — comes straight from
the real daily-location-gallery.html, so a range page generated today
always reflects however that page currently looks and behaves.

This also means: if daily-location-gallery.html's data-loading
<script src> line is ever rewritten (a different mirror path, a
different loading mechanism), the script's exact-match regex
(MIRROR_SCRIPT_TAG_RE) will stop matching, and the script exits with a
clear error instead of silently producing a broken or unscoped page.
Whoever changes that line in daily-location-gallery.html should update
MIRROR_SCRIPT_TAG_RE in this script to match.

How to run it (current)
--------------------------
No dependencies — plain Node.

    node scripts/javascript/build-daily-location-gallery-for-range.js <journal-folder> <start> <end> [output-path]

  <journal-folder> Which trip to generate a range page for, resolved two
                   ways, tried in order: as a path relative to the
                   current directory (or absolute), or as a folder name
                   directly under the travel-journals collection root
                   (e.g. "travel-journal-2026-07-01"). Required.
  <start>/<end>    Inclusive date range, YYYY-MM-DD. Both required.
  [output-path]    Defaults to common/daily-location-gallery-<start>_to_
                    <end>.html. Pass a different path to save under a
                    different name, but it still needs to end up in
                    common/ (next to the template) to actually work.

Example:
    node scripts/javascript/build-daily-location-gallery-for-range.js travel-journal-2026-07-01 2026-07-05 2026-07-13

This writes common/daily-location-gallery-2026-07-05_to_2026-07-13.html.
Opening it in a browser loads the current multimedia-location-data.js
live and shows only 2026-07-05 through 2026-07-13.

Notes and safety
------------------
  - Read-only with respect to daily-location-gallery.html and the data
    files: never modifies any of them. Safe to rerun any time — it
    always regenerates the range page fresh from whatever
    daily-location-gallery.html currently looks like.

  - Requires data/multimedia-location/multimedia-location-data.js (the
    live runtime mirror) to already exist — run
    scripts/javascript/build-multimedia-location-clusters-data.js
    (normal mode, with a synthesis file) first if it's missing.

  - Requires daily-location-gallery.html to already exist at the
    project root, since it's used as the live template.

  - If no clusters currently fall in the date range, the script still
    writes the output file (so the run doesn't just silently fail) and
    prints a WARNING in the preview — but since the data is live, that's
    only a snapshot-in-time warning: if matching days get added to the
    data later, the same generated page will start showing them without
    being regenerated.

  - Output file names collide if you run the same [start, end] range
    twice without specifying a different [output-path] — the second run
    silently overwrites the first with a fresh copy of the current
    template (the underlying data was already live either way, so this
    only matters if daily-location-gallery.html's markup/styling itself
    changed between runs). This is intentional (matches "safe to rerun"
    above), not a bug.

  - Earlier version of this script (superseded): the first version
    inlined a frozen JSON snapshot of the filtered clusters directly
    into the page (window.MULTIMEDIA_LOCATION_DATA = [...] baked in),
    making the output fully self-contained and portable but frozen at
    generation time. That version is no longer what this script does —
    see "Your updated query (verbatim, dynamic data)" above.

Debugging note (2026-08-27): the first version of the marker-matching
regex, /<!-- TRIP-DATA-LOADER-START -->[\s\S]*?<!-- TRIP-DATA-LOADER-END -->/,
failed to match. The START marker's own HTML comment isn't a bare,
empty tag -- it carries explanatory prose and closes with its own "-->"
on the same line (<!-- TRIP-DATA-LOADER-START -- a trip's own build-
daily-location-gallery-for-range.js replaces ... -->), so the literal
substring "TRIP-DATA-LOADER-START -->" never occurs in the template.
Fixed by matching up to that comment's own close first, then on to the
separate, bare TRIP-DATA-LOADER-END comment:
/<!-- TRIP-DATA-LOADER-START[\s\S]*?-->[\s\S]*?<!-- TRIP-DATA-LOADER-END -->/.
