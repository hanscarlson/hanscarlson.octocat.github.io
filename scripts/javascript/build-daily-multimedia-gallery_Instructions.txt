The per-day grid (daily-gallery.html?folder=<date>) has had a slideshow
since the third update: a "Slideshow: Ns" duration dropdown (default 4s)
and a "▶ Slideshow" button in the header, which opens the individual

stopping (not looping) after the last one. The "All Days" day-picker (no
?folder=) had no equivalent — its header-right controls, including the
slideshow ones, are hidden entirely in that view (see renderDayPicker()).

I added a second, parallel set of the same two controls —
#all-slideshow-interval and #all-slideshow-start — to the day-picker's own
toolbar (next to the existing "Date: Oldest/Newest first" day-sort
dropdown, in a new .day-picker-toolbar-right wrapper so the row wraps
sanely on narrow screens), rather than reusing the header's hidden ones:
the header-right block is unconditionally hidden while the day-picker is
showing, so its controls are never clickable there, and duplicate IDs
aren't valid HTML — a second, distinct set was the only option, matching
this script's existing pattern of day-picker and per-day-grid controls
already being separate elements (day-sort vs. sort).

"All files in photos sub folders": clicking "▶ Slideshow" in the
day-picker builds one combined list (buildAllItems()) by concatenating
every day's items — each day's own items in the same oldest-first order
its thumbnail row already shows (sortItems(DATA[folder], "asc")), days
themselves concatenated in the day-picker's current day-sort order (so a
"Date: Newest first" day list starts its slideshow on the most recent
day) — then calls the exact same startSlideshow()/openViewer()/
advanceSlideshow() machinery the per-day grid's slideshow already uses,
just fed this larger `items` array instead of one day's. Every existing
slideshow behavior (stop-not-loop at the last item, the pause/resume
button, manual nav not interrupting it, closing the viewer) is identical
and untouched — nothing about the viewer or slideshow internals is
duplicated, only the two entry-point controls are.

One small refactor this required: startSlideshow() used to always read
the duration from the header's #slideshow-interval select by name. It now
takes that select as a parameter (startSlideshow(intervalSel)) and stores
it in activeSlideshowIntervalSel, which startSlideshowTimer() reads from
instead — so the per-day grid's button passes its own #slideshow-interval
and the day-picker's passes #all-slideshow-interval, and each slideshow
still only reads its own duration once, at the moment it starts, exactly
as before. (The per-day grid's click handler was changed from
`slideshowStartBtn.addEventListener("click", startSlideshow)` to an
explicit wrapper function — passing startSlideshow directly would have
handed it the click MouseEvent as intervalSel instead of the select
element, silently breaking the duration dropdown.)

Closing the viewer (whichever slideshow started it) always returns to
whatever was showing underneath — the day-picker screen, unchanged — the
same way it already did for a single day's slideshow or an individual
thumbnail click; no navigation happens.

          CSS limitation (not specific to this page), and switching
          alignment only while actually zoomed is the standard fix:
          the image still looks centered at rest, and only shifts to
          top-left anchoring once there is real overflow to scroll
          through.

     navigating to a different file) removes the ".zoomed" class and
     resets #stage's scroll position back to 0,0, so the next zoom-in

Claude's resolved query (fifth update — dynamic, runtime-resolved data)
------------------------------------------------------------------------------
Previously, every time this script ran it did all the real work itself, in
Node, at generation time: it grouped the catalog by folder, resolved each
file's sort date, built each file's URL, and picked out its description
text — then froze that entire precomputed result as a JSON snapshot baked
straight into daily-gallery.html (window.DAILY_MULTIMEDIA = {...}). The
page itself did no real data work; it just read that frozen snapshot.
Regenerating daily-gallery.html was therefore required every single time
multimedia-data.json changed, or the gallery would silently show stale
data.

That precomputation has moved out of Node entirely and into
daily-gallery.html's own client-side script, so it happens live in the
browser, every time the page loads:

  - This script's job shrank to two things:
      1. Mirror data/multimedia/multimedia-data.json — as-is, unsorted,
         ungrouped, with no per-item fields added or removed — into a new
         file, data/multimedia/multimedia-data.js, as
         window.MULTIMEDIA_CATALOG = [...]. This mirror step exists only
         because opening an HTML file straight from disk (file://) blocks
         fetch() of local JSON in most browsers, while a classic
         <script src> tag loading a .js file still works fine — the same
         technique gallery.html already uses for manifest.js. No
         computation happens in this step; it is a pure copy.
      2. Write the static daily-gallery.html shell, which now loads that
         mirror via <script src="./data/multimedia/multimedia-data.js">
         and carries no file data of its own.
  - daily-gallery.html's inline script now contains its own copies of the
    date-parsing (parseExifDateTime/resolveDate), URL-building (buildUrl),
    and folder-grouping (buildGroups) logic that used to live in this
    Node script — functionally identical, just running client-side. On
    every page load, it calls buildGroups(window.MULTIMEDIA_CATALOG) to
    produce the same DATA structure the page always used internally; from
    that point on, sorting, thumbnail rendering, the individual viewer,
    slideshow, zoom, and the description toggle all work exactly as
    before, since they only ever consumed that DATA structure, not
    knowing or caring whether it was pre-baked or just computed.
  - Net effect: daily-gallery.html itself is now identical, byte-for-byte,
    from one run of this script to the next, unless the script's own
    template/behavior changes. It never needs to be regenerated just
    because photos were added, folders changed, or new subject_description
    text was filled in — only data/multimedia/multimedia-data.js (the
    trivial raw-data mirror) needs refreshing for that, and reloading the
    already-open page in the browser is enough to pick it up.

What it does
------------
For data/multimedia/multimedia-data.json, build-daily-multimedia-gallery.js:
  1. Mirrors it unchanged into data/multimedia/multimedia-data.js as
     window.MULTIMEDIA_CATALOG — a plain runtime-loadable copy, no
     grouping/sorting/date-parsing/URL-building applied.
  2. Writes the static daily-gallery.html viewer shell, which loads that
     mirror and does all grouping (by folder basename, e.g. "2026-07-10"),
     date resolution (EXIF datetime_original, else
     file_properties.modified_time, else none), URL-building, and
     description lookup itself, at runtime, every time it is opened.

Notes and safety
-----------------
- Read-only with respect to photos/ and data/multimedia/multimedia-data.json
  — this script only ever writes daily-gallery.html and
  data/multimedia/multimedia-data.js (never multimedia-data.json itself).
- daily-gallery.html is a completely separate, additional viewer;
  gallery.html, manifest.js, and index.html's existing "N photos →" links
  are untouched. index.html isn't currently linked to daily-gallery.html —
  ask Claude to add a link/nav entry if you'd like one.
- Videos (multimedia_metadata.type: "video") render with native <video>
  controls instead of the zoom-in/out controls, since there are no video
  files in the catalog yet to test against and native video controls
  already handle their own zoom/fullscreen.
- Dynamic/runtime data: the day picker, every day's thumbnail grid, sort
  order, image/video URLs, and subject_description text are all computed
  live by daily-gallery.html's own script from
  data/multimedia/multimedia-data.js (window.MULTIMEDIA_CATALOG) each time
  the page loads — none of it is written into daily-gallery.html itself.
  Re-run this script after cataloging new photos or filling in more
  descriptions to refresh that mirror file, then reload the page (no need
  to reopen/re-navigate to it — a normal browser refresh is enough).
- If data/multimedia/multimedia-data.js fails to load for any reason (e.g.
  opened before this script has ever been run), daily-gallery.html's
  <script src="./data/multimedia/multimedia-data.js"> tag has an onerror
  fallback that sets window.MULTIMEDIA_CATALOG to an empty array, so the
  page still loads cleanly and shows "No multimedia files found" instead
  of a broken/blank page.
