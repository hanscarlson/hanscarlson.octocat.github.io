DAILY LOCATION GALLERY (common/) — INSTRUCTIONS
===================================================

This file is the design-of-record for common/daily-location-gallery.html
going forward: a single, DYNAMIC page shared by every trip, replacing the
per-trip copies each trip used to carry independently. It picks up the
history where each trip's own build-multimedia-location-clusters-
data_Instructions.txt left off — see the "Prior history" section below
for a pointer to that record, which still covers everything about the
page's look and behavior from before this move.

------------------------

common folder"

Followed by two clarifying answers, since the move raised a real design
question rather than being a plain file relocation:

  Q1: "daily-location-gallery.html currently loads its data via a

Claude's resolved query
--------------------------
A1 meant the page could no longer assume "the trip" the way it always
could assume "the day" — there was nothing left to hardcode a relative
path against. A2 meant the fix had to work for every existing trip, not
just the one that prompted the move, and that this had to become the
one page both trips (and any future trip) point at. Together, that's a
bigger change than moving a file: the page needed a genuine trip
picker, every internal link needed an extra directory level and a
carried-through ?trip=, and the one script that generates a
frozen-to-one-trip derivative of this page (build-daily-location-
gallery-for-range.js) needed to learn how to hardcode a trip at
generation time instead of relying on the page always meaning one trip
implicitly. All of that is what this file, and the four points below,
describe.

WHAT CHANGED
---------------
1. Moved from travel-journal-2026-07-01/daily-location-gallery.html to
   common/daily-location-gallery.html — one directory level above every
   trip folder, sibling to travel-journals/index.html and the top-level
   scripts/ folder (not inside any one trip).

2. Trip-agnostic via ?trip=<folder>. The page now shows one of four
   states depending on its URL:
     (neither param)      Trip picker — one card per trip in
                           data/trips-manifest.js, pick one.
     ?trip= only           Day picker for that trip — every date present
                           in that trip's own data.
     ?trip=&date=           That day's location galleries — same as
                           before the move.
     ?trip=&date= (no match) Empty state — same as before the move.
   See the page's own top comment for the full parameter reference, the
   two runtime-mirror data sources it loads (data/trips-manifest.js and
   ../<trip>/data/multimedia-location/multimedia-location-data.js), and
   why a document.write()-based loader is used for the second one (the
   trip isn't known until the URL is parsed, so a plain static
   <script src> tag can't name its path ahead of time).

3. Every internal link gained a "../<trip>/" prefix and a carried ?trip=
   parameter — daily-gallery.html links, the journal's own index.html
   link, and next/prev/first/last day-jump links (all four, from the
   Turn 2 First/Prev/Next/Last work — see "Prior history" below) all
   still resolve correctly, now one directory level up and scoped to
   whichever trip is currently showing.

4. scripts/javascript/build-common-trips-manifest.js (NEW) scans every
   travel-journal-YYYY-MM-DD folder's own index.html for its title and
   subtitle and writes common/data/trips-manifest.js — the data source
   the trip picker (point 2 above) and each page's masthead title read.
   See that script's own Instructions.txt for the full design; briefly,
   it exists because a browser can't list sibling folders on disk
   (file:// has no directory API), so — like every other piece of data
   this project's pages need from outside their own folder — it's
   bridged with a small build script that writes a plain runtime-mirror
   .js file.

5. Each trip's own scripts/javascript/build-daily-location-gallery-for-
   range.js — the script that freezes this page to one trip and a fixed
   date range for a bare, shareable link — was updated to read the new
   common/ template and hardcode window.TRIP_OVERRIDE instead of relying
   on the page implicitly meaning one trip. See that script's own
   Instructions.txt (in each trip's own scripts/javascript/) for the
   full design and a debugging note about the marker-comment regex fix
   made along the way.

6. Each trip's own scripts/javascript/build-travel-journal.js was
   updated so every day's photo-link href points at
   ../common/daily-location-gallery.html?trip=<folder>&date=<date>
   instead of ./daily-location-gallery.html?date=<date>. See that
   script's own Instructions.txt for the specific before/after.

7. travel-journal-2026-01-14's own separate, older copy of daily-
   location-gallery.html was retired (deleted) — it now uses this same
   shared page, picking up every update travel-journal-2026-07-01's copy
   had already received (the day-jump links and British Read Aloud voice
   from Turn 2) that its own copy had been missing.

HOW TO RUN / REGENERATE THE PIECES THIS MOVE ADDED OR CHANGED
-------------------------------------------------------------------
  New trip added: run, in order —
    node scripts/javascript/build-common-trips-manifest.js
        (from the travel-journals/ root — rescans every trip's
        trip-info.json and rewrites common/data/trips-manifest.js so the
        trip picker and masthead titles include the new trip)

  A trip's data changes (new days, re-clustered, re-synthesized):
    no action needed for common/daily-location-gallery.html itself — it
    reads that trip's data/multimedia-location/multimedia-location-
    data.js live, every time it's opened. Only re-run
    build-common-trips-manifest.js if the trip's own trip-info.json
    title changed.

  A trip's photo-links need to point at the common page (new trip,
  never rebuilt before):
    No rebuild needed -- every trip's journal page is
    common/journal.html?trip=<folder>, a client-side-rendered page
    shared by every trip (see scripts/_to_delete/build-travel-
    journal_Instructions.txt for how it replaced the old build-time
    index.html this section originally described, and the "Update"
    section at the end of this file for how that page later moved from
    a per-trip index.html to this shared one) whose photo-links already
    point at the common page directly; TRIP_FOLDER is read from the
    page's own URL at load time, not baked in at build time.

  A trip's range-scoped derivative needs regenerating:
    node scripts/javascript/build-daily-location-gallery-for-range.js <start> <end>
        (from inside that trip folder — see that script's own
        Instructions.txt)

Notes and safety
-------------------
- This file documents the page's own markup/CSS/JS going forward. Data-
  producing scripts (build-multimedia-location-clusters-data.js,
  refresh-events.js, refresh-notes.js, etc.) keep their own
  Instructions.txt files inside each trip folder, unchanged by this
  move.
- ?trip= is validated against /^[A-Za-z0-9_.-]+$/ before ever being used
  to build a path or a document.write() string — an invalid or missing
  value is treated exactly like no ?trip= at all (shows the trip
  picker), never an error page.
- The page has no way to discover trip folders itself (file:// pages
  can't list a directory) — data/trips-manifest.js is the only source
  the trip picker and per-trip titles read, so it must be re-run
  whenever a trip is added, removed, or renamed, or its own trip-
  info.json title changes. A stale or missing manifest just means the
  trip picker is incomplete or empty, not broken.

Update — Fixed: Read Aloud button text not resetting after Stop (2026-08-27, same day)
--------------------------------------------------------------------------------------------------
Your query (verbatim): "the "Read Aloud" link when toggled to "Stop
Reading" and clicked again stops reading, but does not reset the link
text to "Read Aloud""

Bug: setupReadAloud() clones the button node (cloneNode + replaceChild)
right before attaching its click listener, specifically so each call to
renderDay() gets a listener bound only to that day's own segments
without stacking duplicate listeners from previous days. Everything
after the clone -- the click handler, speakNext(), setIdle() -- must
operate on that new freshBtn, since the original btn reference is now a
detached node no longer in the page. Two places correctly did this
(freshBtn.textContent = 'Stop Reading' when starting, in the click
handler) but setIdle() -- called both when the user clicks Stop and
when speech reaches the end of the segments on its own -- was still
written against the stale outer btn, so it silently updated a node the
user could no longer see instead of the visible one. Net effect: the
click did stop the speech (synth.cancel() runs fine, it doesn't care
which node called it) but the button visibly stayed on "Stop Reading".
Fixed by pointing setIdle()'s two lines at freshBtn instead of btn.

Verified: inline <script> blocks syntax-checked with node --check
(pass). Reproduced the exact reported symptom against the pre-fix code
via Playwright with speechSynthesis.speak()/cancel() stubbed out (so
the click path could be tested deterministically, independent of
whether a given browser/engine actually has a TTS voice available) --
confirmed the button stayed on "⏹ Stop Reading" with the .reading class
still applied after the second click. Ran the identical test against
the fixed code: after the second click the button correctly reads "🔊
Read Aloud" with the .reading class removed. Also re-ran the full
1500/1100/420px screenshot + overflow check as a regression guard,
since deploys in this session always get the full pass even when a
change is JS-only -- no visual difference, no horizontal overflow.

Update — days with no clustered location render as a location of their own (2026-08-29)
